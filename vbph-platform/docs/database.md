# Database architecture

Covers `supabase/migrations/*.sql` as of the schema-implementation pass (8 migrations, `20260813040822` through `20260813223411`). This is schema + RLS only — no application code queries most of these tables yet (see each table's "Consumed by" note).

## Tables

| Table | Purpose | Key columns |
|---|---|---|
| `profiles` | One row per `auth.users` row. Source of truth for app role. | `id` (=auth.users.id), `role` (CLIENT/VA/ADMIN), `status` (active/suspended) |
| `va_profiles` | Extended VA profile + marketplace approval gate. | `id` (=profiles.id), `skills[]`, `approval_status` |
| `clients` | A company record. | `company_name`, `status` |
| `client_members` | Which profiles belong to which client company. | `client_id`, `profile_id`, `role_in_company` (owner/member) |
| `projects` | Client-owned unit of work a placement can attach to. | `client_id`, `status` |
| `jobs` | A client's job posting. **Rate-sensitive.** | `client_hourly_rate`, `agency_margin`, `va_hourly_rate` (generated), `status` (DRAFT/OPEN/PAUSED/FILLED/CLOSED), `required_skills[]`, `experience_level`, `num_vas_required`, `application_deadline` |
| `job_applications` | A VA applying to a job. | `job_id`, `va_id`, `status` |
| `placements` | Client/VA/job/project assignment, rates **snapshotted** here. **Rate-sensitive.** | `client_hourly_rate`, `agency_margin`, `va_hourly_rate` (generated) |
| `time_entries` | A timer session. | `placement_id`, `started_at`/`ended_at`, `status` (pending/approved/rejected) |
| `time_segments` | A ≤10-minute increment within a session — the atomic billable unit. | `time_entry_id`, `segment_start`/`segment_end`, `activity_percentage` |
| `screenshots` | One per segment. | `time_segment_id` (unique) |
| `timesheets` | One per (placement, ISO week). Hours are live-computed until `LOCKED`, then frozen. | `placement_id`, `week_start`/`week_end` (generated), `status` (OPEN/SUBMITTED/APPROVED/LOCKED), `tracked_hours`/`approved_hours`/`rejected_hours`/`pending_hours` (NULL until locked) |
| `invoices` | A client's weekly invoice, generated from that client's `LOCKED` timesheets. | `client_id`, `invoice_number`, `period_start`/`period_end`, `due_date`, `status` (DRAFT/ISSUED/PAID/OVERDUE/VOID) |
| `invoice_items` | Line items — **client rate is correct here**, this is a client-facing document. **VA rate/payout/margin are admin-only.** | `invoice_id`, `placement_id`, `hours`, `rate_hour`, `amount` (generated), `va_hourly_rate`, `va_payout_amount`/`margin_amount` (generated, admin-only) |
| `payments` | Payment records against an invoice. | `invoice_id`, `provider`, `status` |
| `audit_logs` | Append-only action log. | `actor_id`, `action`, `target_table`/`target_id`, `metadata` |

Relationship shape: `clients` 1—N `client_members`/`projects`/`jobs`/`invoices`; `jobs` 1—N `job_applications`; `placements` references `clients` + `va_profiles` + optionally `jobs` + `projects`; `time_entries` → `placements`; `time_segments` → `time_entries`; `screenshots` → `time_segments`; `timesheets` → `placements`; `invoice_items` → `invoices` + `placements`.

## The rate-privacy mechanism

This is the part worth understanding before changing anything in `jobs`, `placements`, or the views migration.

1. **`va_hourly_rate` is a `GENERATED ALWAYS AS (client_hourly_rate - agency_margin) STORED` column**, on both `jobs` and `placements`, with a `CHECK (va_hourly_rate >= 0)`. Postgres physically rejects any attempt to write to a generated column — so "don't compute the VA rate in JavaScript" isn't a convention here, it's structurally impossible to violate. A negative rate (margin exceeding the client rate) is equally impossible to persist. Verified empirically (see `docs/database.md#verification` below).

2. **The base `jobs` and `placements` tables have no SELECT policy for `CLIENT` or `VA`** — only `ADMIN`. Additionally, `SELECT` is explicitly `REVOKE`d from `authenticated` on both tables (belt-and-suspenders: even a future migration that accidentally added a bad policy wouldn't expose them, since the table-level grant is closed independently of RLS).

3. **`client_jobs_view` / `va_jobs_view` / `client_placements_view` / `va_placements_view`** are the only read path those two roles have. Each is a plain view (`security_invoker = false`, set explicitly) owned by the migration role — Postgres never applies RLS to a table/view's owner, so the view can read every row of the base table internally, while:
   - its **column list** never includes the columns that role shouldn't see (not filtered — structurally absent from the output), and
   - its own **`WHERE` clause** (written by us, e.g. `is_client_member(client_id)`) is the actual row-scoping logic, since the base table's RLS isn't what's running here.

   | View | Shows | Hides | Row scope |
   |---|---|---|---|
   | `client_jobs_view` | `client_hourly_rate` | `agency_margin`, `va_hourly_rate` | own company's jobs (any status) |
   | `va_jobs_view` | `va_hourly_rate` | `client_hourly_rate`, `agency_margin` | open marketplace jobs + jobs applied/placed on |
   | `client_placements_view` | `client_hourly_rate` | `agency_margin`, `va_hourly_rate` | own company's placements |
   | `va_placements_view` | `va_hourly_rate` | `client_hourly_rate`, `agency_margin` | own placements |

4. Invoices/invoice_items are **not** part of this mechanism — `invoice_items.rate_hour` is the client rate, shown on the client's own invoice, which is correct and expected.

5. **Column-level `GRANT`s close the write side of the same gap.** RLS decides *which rows* a role can touch; it says nothing about *which columns* of an allowed row a write may set. `authenticated` has table-level `INSERT`/`UPDATE` on `jobs` (from `fix_baseline_grants.sql`) but only *column*-level grants on the client-editable fields (title, description, rate, schedule, etc.) — `agency_margin` and the generated `va_hourly_rate` are never granted. A client INSERT/UPDATE that tries to set `agency_margin` directly (e.g. a hand-crafted PostgREST request bypassing the UI entirely) gets `permission denied for table jobs`, not a silently-ignored field. Verified empirically (job_posting_fields migration) — see Verification below.

6. **`id` is grantable for INSERT specifically so the app can avoid `RETURNING`.** Because `jobs` has no SELECT grant at all for `authenticated`, `INSERT ... RETURNING id` fails (RETURNING needs SELECT). The Server Action generates the UUID client-side (`crypto.randomUUID()`) and inserts it explicitly, so it knows the new row's id for the post-create redirect without ever reading the row back through the base table.

## RLS helper functions

All `SECURITY DEFINER` (bypass RLS on the table they check, which is what lets a policy on table A check a condition on table B without recursively hitting B's own RLS), all `STABLE`.

- `current_user_role()` — the caller's `profiles.role`, or NULL.
- `is_admin()` — NULL-safe `current_user_role() = 'ADMIN'`. **Use this, not the raw comparison, in any new plpgsql function** — see the note below.
- `is_client_member(client_id)` / `is_client_owner(client_id)`
- `client_owns_job(job_id)`, `va_is_approved()`
- `va_owns_placement(placement_id)`, `client_owns_placement(placement_id)`, `va_has_placement_on_project(project_id)`
- `va_owns_time_entry(...)`, `client_owns_time_entry(...)`, `va_owns_time_segment(...)`, `client_owns_time_segment(...)`
- `client_owns_invoice(invoice_id)`
- `delete_screenshot(screenshot_id)` — not a boolean helper, an RPC: authorization-checked deletion that cascades to the parent `time_segment` (see comments in the time-tracking migration for why this is a function and not just an RLS DELETE policy).

### A real bug this testing caught

The "chained" helpers above (e.g. `client_owns_placement`) are of the shape `select is_client_member(client_id) from placements where id = $1`. If `$1` doesn't match any row, that returns **SQL NULL, not `false`**. That's harmless inside an RLS `USING` clause (NULL denies the row, same as false) — but it's a live bug inside plpgsql: `if not (false or null) then` evaluates to `if null then`, and plpgsql treats a NULL condition as "not met," **silently skipping the exception it was supposed to raise**. This exact bug shipped in an early draft of `delete_screenshot()` and was only caught by actually running an unauthorized-deletion test against it (see Verification below) — it returned success instead of raising `Not authorized`. Fixed by wrapping every such helper's result in `coalesce(..., false)` at the source, and by using `is_admin()` (NULL-safe) instead of the raw `current_user_role() = 'ADMIN'` comparison in plpgsql going forward.

### Two more bugs found building the Job Posting feature (`job_posting_fields` migration)

Both were dormant since the original schema pass — every RLS policy *looked* correct, and nothing exercised a client-initiated `UPDATE` on `jobs` (or, it turned out, on `clients`/`projects`/`profiles`/`va_profiles`) until this feature tried to.

1. **A `FOR UPDATE` policy without an explicit `WITH CHECK` doesn't inherit its own `USING` clause once another applicable policy supplies an explicit `WITH CHECK`.** `jobs_update_owner` had `USING (is_client_owner(client_id))` and no `WITH CHECK`; `jobs_admin_all` is a separate `FOR ALL` policy with an explicit admin-only `WITH CHECK`. Permissive policies OR together, but a policy that omits `WITH CHECK` contributes *nothing* to that OR-set — it does not fall back to its own `USING`. The effective `WITH CHECK` for `UPDATE` collapsed to admin-only, so a client owner could never complete a job update: `EXPLAIN` on the live policy showed the planner's filter as `(is_client_owner(...) OR is_admin) AND is_admin`. Fixed by giving `jobs_update_owner` (and the same-shaped `clients_update_owner`, `projects_update_owner`, `profiles_update_admin`, `va_profiles_update_admin`) an explicit `WITH CHECK` matching its `USING` clause. Found by auditing every `UPDATE`/`ALL` policy pair in the schema once the `jobs` instance turned up (`select tablename, policyname, cmd, qual is not null, with_check is not null from pg_policies where cmd in ('UPDATE','ALL')`).

2. **`UPDATE ... WHERE` needs SELECT-level RLS on the columns in the `WHERE` clause — independent of `UPDATE` policies entirely.** Per Postgres's own docs, an `UPDATE`'s `WHERE` clause is evaluated under the table's *SELECT* policies, not its `UPDATE` policies, because determining which rows match requires reading them. `jobs` deliberately has zero SELECT policies for CLIENT/VA (that's the whole rate-privacy mechanism above) — so even after fixing bug 1, `UPDATE jobs SET title = ... WHERE id = ? AND client_id = ?` matched zero rows for every client, always. `clients`/`projects`/`profiles`/`va_profiles` were unaffected by this half, since each already has its own SELECT policy for the relevant role. Fixed with a narrow policy, `jobs_select_owner_columns FOR SELECT USING (is_client_owner(client_id))` — safe *only* in combination with bug-3's-fix below (the column grant), since RLS alone doesn't limit which columns a permitted row exposes.

Both were only found by running the actual UPDATE as the actual role (`SET ROLE authenticated; SET request.jwt.claims = ...`) and reading `EXPLAIN`'s filter text, not by re-reading the policy SQL — the catalog (`pg_policies`) reports each policy's clauses correctly in isolation; the bug is only visible in how Postgres *combines* them at plan time.

- Valid job rate ($6 client / $2 margin) → `va_hourly_rate` computes to $4. ✓
- Margin exceeding client rate → `CHECK` constraint rejects the insert. ✓
- Direct `INSERT ... (va_hourly_rate) VALUES (...)` → Postgres rejects it (generated column). ✓
- `time_segments` longer than 10 minutes → `CHECK` constraint rejects it. ✓
- `delete_screenshot()` called by the owning VA → deletes both the screenshot and its `time_segment`. ✓
- `delete_screenshot()` called by an unrelated user → raises `Not authorized` (after the NULL-coalesce fix above — initially did *not* raise, which is how the bug was found). ✓
- VA querying `jobs`/`placements` directly → `permission denied for table jobs` (table-level REVOKE, not just an empty RLS result). ✓
- VA querying `va_jobs_view` → sees `va_hourly_rate`, column list has no `client_hourly_rate`/`agency_margin` at all. ✓
- Client querying `client_jobs_view` → sees `client_hourly_rate`, column list has no `va_hourly_rate`/`agency_margin`. ✓
- Client querying `va_placements_view` (wrong view) → 0 rows. VA querying `client_jobs_view` → 0 rows. ✓
- `supabase/seed.sql` runs end-to-end (structurally verified against the stub `auth.users`; the real `auth.users` insert columns follow the standard documented Supabase local-seeding shape but haven't been run against real GoTrue/Docker — worth a first `supabase db reset` check when Docker's available).

The above was the original schema-only pass, verified against a hand-built Postgres stub before real Docker/Supabase was available in this environment. Since then, all verification runs against a real local stack (Colima + `supabase start`), with role-switched `psql` (`SET ROLE authenticated; SET request.jwt.claims = '...'`) plus Playwright-over-CDP for real browser sessions. From the Job Posting feature specifically:

- Client sets `agency_margin` directly on INSERT or UPDATE → `permission denied for table jobs` (column grant, not RLS). ✓

## The Admin Portal (`admin_portal` migration)

Three additions, all born from bugs found while building the Admin Portal — not designed up front.

1. **Two privilege-escalation triggers.** `profiles_update_own` and `va_profiles_update_own` both have a `WITH CHECK` of just `id = auth.uid()` — correct for "can only touch your own row," but it never scrutinized *which columns* changed. Since CLIENT/VA/ADMIN are all the same Postgres role (`authenticated`), column-level `GRANT`s can't fix this either — any grant broad enough to let a user edit their own `full_name` is automatically broad enough to attempt `role` or `approval_status` too. Confirmed empirically before the fix: as a CLIENT, `update profiles set role = 'ADMIN' where id = auth.uid()` succeeded; as a pending VA, `update va_profiles set approval_status = 'approved' where id = auth.uid()` succeeded. Fixed with `BEFORE UPDATE` triggers (`prevent_self_privilege_escalation`, `prevent_self_approval`) — triggers have real `OLD`/`NEW` access and run regardless of which policy admitted the write, which a `WITH CHECK` alone doesn't give you. Each trigger has an `auth.uid() is null` escape hatch, so seed.sql's own admin-bootstrapping (`update profiles set role = 'ADMIN' ...`, run as `postgres` with no session) and the service-role client both still work — matching `handle_new_user()`'s existing precedent that admin accounts are created only through trusted, non-session paths.

2. **`admin_jobs_view` / `admin_placements_view`** — the one place `client_hourly_rate`, `agency_margin`, and `va_hourly_rate` are ever shown together. Every other view in this schema deliberately exposes only one side (see the rate-privacy section above); these two exist solely for the Admin Portal, `where is_admin()` with no membership OR-clause, so a non-admin gets zero rows even with a table-level grant.

3. **`admin_update_job_rates()` / `admin_update_placement_rates()` RPCs** — "client rate, VA rate, and margin must stay mathematically consistent when manually changed" is enforced by construction: both functions accept only `new_client_hourly_rate` and `new_va_hourly_rate`, compute `margin = client_rate - va_rate` themselves, and write both columns (plus an `audit_logs` row with before/after) in one transaction. There is no code path where a caller supplies margin directly, so it can never disagree with the other two. `SECURITY DEFINER` + an explicit `is_admin()` check, same reasoning as `delete_screenshot()`: `authenticated` has no column grant for `agency_margin` on either table at all, so a plain `UPDATE` — even from an admin session — fails on the grant check before RLS runs. The Admin Portal's rate-override forms only ever expose two number inputs (Client Rate, VA Rate); Margin is always a live-computed, read-only preview, never itself submitted.

**A Zod gotcha specific to this project's seed data**: Zod v4's `.uuid()` enforces the RFC 4122 version/variant nibbles strictly. This project's hand-crafted seed ids (`b0000000-0000-0000-0000-000000000002`, etc.) are valid 8-4-4-4-12 hex GUIDs but not RFC 4122 UUIDs — every one of them fails `.uuid()`. It surfaced as the Admin Portal's placement-creation form always rejecting a validly-selected client with "Select a client," even though the browser was sending the correct value the whole time — confirmed by tracing the raw `FormData` client-side, then server-side, before finally testing the schema in isolation. Fixed by using `.guid()` (shape-only, no version/variant check) everywhere an id from this dataset might arrive — see `packages/schemas/src/admin.ts`. Real `gen_random_uuid()` output (used for every row not seeded by hand) satisfies `.guid()` too, so this is a seed-data accommodation, not a real-world validation loosening. **Use `.guid()`, not `.uuid()`, for any new schema field that validates an id from this project.**

- Client `update profiles set role = 'ADMIN' where id = auth.uid()` → rejected (`Only an admin can change role or status.`); same client editing their own `full_name` → still succeeds. ✓
- Pending VA self-approving their own `va_profiles` row → rejected; admin approving it → succeeds. ✓
- `admin_jobs_view`/`admin_placements_view` as a client → 0 rows, even though the same client can read the row through `client_jobs_view`. ✓
- `admin_update_job_rates(job, 10.00, 6.50)` → `client_hourly_rate=10.00, agency_margin=3.50, va_hourly_rate=6.50`, plus a `job_rates_updated` audit_logs row with before/after values; called by a non-admin → `Not authorized`; called with a VA rate exceeding the client rate → rejected by the pre-existing `jobs_agency_margin_check` CHECK constraint (negative margin), not a new one. ✓
- Placement creation end-to-end through the Admin Portal UI: Client Rate/VA Rate typed in → Margin preview updates live → submit → row persists with exactly the entered rates and the correct computed margin. ✓
- A newly admin-created user (email/password/role via the Auth Admin API) can immediately log in and lands in the correct portal for their role. ✓

## The hiring/placement workflow (`hiring_workflow` migration)

`placements.status` gained `PENDING` (`PENDING → ACTIVE → PAUSED/ENDED`, all uppercase now, matching `jobs.status`) — "hired, not yet started" as a distinct state before a placement is visible to anyone but the admin who created it.

**Rate history, enforced by where the data lives, not by a rule.** The create-placement form copies `client_hourly_rate`/`va_hourly_rate` from the selected job's *current* rate as a one-time starting value (see `getJobOptions` in `server/queries/admin/jobs.ts`) — but that's a plain form default, not a link. Once `createPlacementAction` inserts the row, the placement's own `client_hourly_rate`/`agency_margin` columns are the only thing ever read again; nothing about them references `jobs` going forward. A later `admin_update_job_rates()` call only ever touches the `jobs` row it's given. There was no code to write here that could make a job-rate change retroactively affect an existing placement — the two tables have simply never been connected after insert time, which is what this section's verification confirms empirically rather than assumes.

**"The job can be marked FILLED when the required number of VAs has been hired"** is automatic, not a manual button: `createPlacementAction` counts the job's non-`ENDED` placements after every insert and sets `jobs.status = 'FILLED'` once that count reaches `num_vas_required` (skipped if the job is already `FILLED`/`CLOSED`). It does not reverse itself if a placement later ends — a completed hire doesn't retroactively reopen the req; admin can always reopen a job manually via the existing status control if needed. The same action also opportunistically syncs the matching `job_applications` row to `HIRED` if one exists and isn't already — covers creating a placement directly rather than through the "Create Placement" link on a HIRED application, without leaving that application stuck at an earlier status.

**Two more gaps found building this, same shape as ones already documented above:**

1. **A VA could never see their own placement's client name.** `projects` already had `projects_select_va` (`va_has_placement_on_project`); `clients` had no VA-facing SELECT policy at all — a VA with an active placement got zero rows querying their own client's `company_name`, confirmed empirically before the fix. Added `clients_select_va`, mirroring the existing project policy exactly (`va_has_placement_with_client`, same `EXISTS ... placements WHERE ... AND va_id = auth.uid()` shape).

2. **`updatePlacementStatusAction` had been silently broken since the Admin Portal phase.** Same root cause as the `jobs` UPDATE gap documented above: `placements` has SELECT fully revoked from `authenticated`, and `UPDATE ... WHERE id = ?` needs column-level SELECT on `id` to evaluate that WHERE clause, independent of RLS. `admin_update_placement_rates()` never hit this (it's SECURITY DEFINER, no grant dependency), which is exactly why the gap went unnoticed through the whole Admin Portal test pass — nothing had exercised a plain `.update()` against `placements` end-to-end until this feature tried to activate one. Unlike `jobs`, `placements` has exactly one applicable policy (`placements_admin_all`, no client/VA policy at all), so the fix is a single blanket `grant select on placements to authenticated` rather than a narrow per-column grant — RLS alone still returns zero rows for any non-admin regardless of what's grantable, verified below the same way `application_admin_notes`' equivalent claim was.

### Verification

- Client Rate/VA Rate on the create-placement form pre-fill from the selected job's live rate the moment a job is chosen (and immediately, if arriving via a HIRED application's "Create Placement" link with a job pre-selected) — editable before submit, but that's the only time they're ever copied. ✓
- Placement created at $8.50/$6.00 → job's rate later changed to $20.00/$15.00 via `admin_update_job_rates` → placement, re-read from the DB, still shows exactly $8.50/$6.00. ✓
- Creating a placement for a job with `num_vas_required = 2`: after the 1st placement, job stays `OPEN` (`1 / 2` hired); after the 2nd, job flips to `FILLED` automatically (`2 / 2`), with a `job_status_changed` audit_logs row (`reason: required_va_count_reached`). ✓
- Creating a placement directly (not via the application's "Create Placement" link) for a job/VA pair with an existing non-HIRED application → that application flips to `HIRED` too. ✓
- The "Create Placement" action is only reachable from an application's detail page once its status is `HIRED` — absent otherwise. ✓
- After activating a placement (`PENDING → ACTIVE`): the client's dashboard shows the VA under My Team with the client's own rate; the VA's dashboard shows the client/project with the VA's own rate. Each page's raw HTML checked for the other side's rate value and for the `client_hourly_rate`/`va_hourly_rate`/`agency_margin` key names — absent in both directions. ✓
- `clients_select_va`: a VA with a placement at a client reads that client's `company_name`; a VA with no placement there gets zero rows for the same query. ✓
- `grant select on placements`: admin can now complete a plain status UPDATE (previously `permission denied for table placements`); CLIENT and VA sessions still get zero rows from a raw `select * from placements`, confirming the grant didn't reopen the rate-privacy gap the base table's SELECT revoke was there to close. ✓

## The time-tracking API (`time_tracking_api` migration)

Real HTTP endpoints (`apps/web/src/app/api/time/**/route.ts`), not Server Actions — the point of this pass was building the backend the future desktop app will call, and Server Actions are tied to this Next.js app's own client-side runtime in a way a separate Electron/Tauri process can't invoke. Auth is a bearer access token (`apps/web/src/lib/api/auth.ts`), not the cookie session every other part of this app uses: the desktop app authenticates directly against Supabase Auth (same `signInWithPassword` flow as the web app) and sends the resulting token on every request. `authenticateApiRequest()` creates an RLS-scoped client from that token via `supabase.auth.getUser(token)` (the stateless "verify a token I was just handed" form — not `getClaims()`, which introspects a session this client never established) — RLS is still the real enforcement, exactly as everywhere else.

**What's deliberately not in `time_segments`, ever**: actual keystrokes, passwords, clipboard contents, URLs, or message contents. `keyboard_activity_count`/`mouse_activity_count` are counts of input events, never the events themselves. A future URL-tracking feature would be a new, explicit column and a new conversation about scope — not something that piggybacks on these.

**Segment boundaries are immutable after creation, activity fields aren't** — `time_segments` had SELECT/INSERT policies but no UPDATE policy at all before this ("Record Activity" had no path). RLS can't express "this row is editable but only some of its columns" (a `WITH CHECK` only sees the proposed new row, not which columns changed) — same shape as the `jobs.agency_margin` gap documented above — so `segment_start`/`segment_end`/`time_entry_id` stay fixed via a column-level `GRANT` that simply never includes them, while `keyboard_activity_count`/`mouse_activity_count`/`activity_percentage`/`memo` are grantable. Without this, a VA could silently extend their own billable time by editing `segment_end` after the fact.

**Screenshots: private bucket, no Storage RLS policies, service-role client only inside already-authorized code.** The `screenshots` bucket is created with `public = false` — Storage rejects any anonymous read regardless of what else is configured. No `storage.objects` policies are added for `authenticated` either; every file operation (upload, signed URL, delete) goes through the service-role client (`lib/supabase/admin.ts`), called only from inside a Route Handler that has already done a normal RLS-scoped read to establish the caller is allowed to touch that row. The service role never substitutes for an authorization check — it only reaches Storage after one has already passed. Signed URLs are generated fresh per request (5 minute TTL) and only for screenshot rows the caller's own RLS-scoped query already returned — there's no separate "check if this user can see this screenshot" step, because the DB read that produced the row *is* that check.

**A real, pre-existing access gap found wiring the session DTO together**: `placements` has exactly one RLS policy, `placements_admin_all` (admin-only) — confirmed earlier in this doc, but its consequence hadn't surfaced yet because nothing had queried the base table directly as a VA or CLIENT until this feature tried to. `toSessionDto()`'s first version read `va_id`/`project_id` straight from `placements`, which silently returned nothing for non-admin callers (not an error — `.maybeSingle()` on an RLS-emptied query just returns `null`), producing sessions with an empty `vaId` and a null `projectId` for every VA and client caller. Fixed by reading through `va_placements_view` first, falling back to `client_placements_view` — the same two non-rate-sensitive columns (`va_id`, `project_id`) are present in both, so trying VA's own view then the client's covers all three caller roles without ever touching a rate column that view wasn't meant to expose to that role.

**"Total Time" is computed from segments, not wall-clock `ended_at - started_at`.** Segments are "the atomic billable unit" (see the original time-tracking migration's own framing); summing them is what's actually billable, and doesn't overcount a session that had an idle gap never covered by a segment.

## The Work Diary interface

Three portal pages (`/va/work-diary`, `/client/projects/[projectId]/work-diary`, `/admin/time`) built entirely on top of the time-tracking backend's own `service.ts` functions — no new tables, no new RLS. This is the payoff of that phase's "create clear backend functions" instruction: the web UI needed zero new authorization logic, just a new presentation layer over functions that already enforced access.

**Chronological display, day/week navigation, and the Total/Approved/Rejected stats are all derived, not stored.** `getWorkDiaryBlocks()` resolves an optional `projectId` filter down to placement IDs, queries `time_entries` (RLS-scoped, so a VA/CLIENT session only ever sees rows it's already allowed to see) within the date range, batch-fetches every matching `time_segments` row, joins in `screenshots` + fresh signed URLs, and assembles one block per segment ordered by `segment_start`. The summary is a single reduce over those blocks, bucketing by the parent `time_entries.status` (`approved`/`rejected`/`pending`) — there's no separate approved/rejected total anywhere in the schema to go stale.

**The confirmation copy is caller-supplied, not hardcoded in the shared `DiaryBlockCard`.** The VA page passes the exact required sentence ("Deleting this screenshot will also remove this time segment from your tracked hours."); the admin page passes a variant that additionally states the action is audit-logged. **Only the admin delete path writes to `audit_logs`; the VA's own delete does not** — same convention as every admin mutation in the Admin Portal phase (`logAdminAction()` is only ever called from admin-gated Server Actions). `adminDeleteSegmentAction` deliberately does three sequential reads (`screenshots` → `time_segments` → `time_entries`) *before* calling `deleteScreenshot()`, purely to capture `segmentStart`/`segmentEnd`/`memo`/`placementId` for the audit row — the alternative (a nested PostgREST embed in one query) is fragile against the same base-table SELECT-revoke pattern documented throughout this file, and the row is about to be deleted anyway so there's no correctness reason to save one round trip.

**A new `Modal` component (`packages/ui`) — this package's first — needed `packages/ui/tsconfig.json` to add `"lib": ["ES2022", "DOM", "DOM.Iterable"]`, overriding the shared base config's DOM-less `lib` array.** Every prior component in this package only needed React's own element types (`HTMLInputElement` etc., which ship with `@types/react` independent of the `lib` array), so this was never hit before. ## The desktop Time Tracker app (`apps/desktop`)

Tauri v2 + React + TypeScript, at `apps/desktop` in the monorepo — the first non-Next.js app here. It is a thin client: it never touches the database directly except for authentication. Everything else (placements, timer start/stop, segment recording) goes through the exact same `apps/web/src/app/api/time/*` Bearer-token endpoints the previous phase built specifically for this — see "The time-tracking API" above. Three small endpoints were added to that surface for this app's own needs, each a thin wrapper over a new `service.ts` function: `GET /api/time/me` (confirm the token is valid and the account is a VA — used right after login and on every cold start), `GET /api/time/placements` (this VA's `ACTIVE`-only placements — narrower than the web dashboard's own `getVaPlacements`, which also shows `PAUSED`; a desktop timer has no use for a placement it isn't allowed to clock into right now), and `GET /api/time/entries/active` (this VA's currently-running sessions — the source of truth for restart recovery, returning an array since `startTimer`'s own "already running" guard is only scoped per-placement, not per-VA).

**No Supabase service-role key anywhere in this app — by construction, not by discipline.** Login calls Supabase Auth's REST API directly (`signInWithPassword`/`refresh_token` grant) with only the public anon key, exactly as `apps/web/src/lib/api/auth.ts` already documented the desktop app would; every other request carries the resulting user JWT as a Bearer token, and RLS is what actually authorizes it, same as the web app's own browser bundle. `apps/desktop/.env.local.example` says so directly: everything in that file ends up in the compiled binary, so it may only ever contain values already safe to hand to any client.

**Secure session storage is two-tiered, split by how long each half lives.** The short-lived access token is kept in memory ONLY — never written to disk. The long-lived refresh token (plus the VA's id/email, for re-persisting after Supabase's own token rotation) is the one thing that survives an app restart, and it lives in the OS's real credential store — macOS Keychain / Windows Credential Manager / Linux Secret Service — via three Rust commands (`secure_store_save/load/clear`, `apps/desktop/src-tauri/src/secure_store.rs`) built on the `keyring` crate, never a plaintext file. `authStore.ts` proactively refreshes ~60s before expiry and reactively retries once on any 401; a refresh that fails because the network is unreachable leaves the stored session alone (`offline-locked` state — a stored session isn't wrong just because it can't be verified right now); a refresh that fails because Supabase actually rejects the token (revoked/expired) clears the stored session and returns to `signed-out` with a "session expired" message, so a dead session can't loop forever.

**Local-safe recovery for unsynced timer data — `localStore.ts` + `offlineQueue.ts`.** Every segment (and the final stop-of-timer call) is written to a persisted queue FIRST, then flushed to the server — never held only in memory. A currently-running timer also has a local "active session marker" (placement/entry id, server start time, current segment's start, task memo) persisted on every tick and every rollover, both backed by the official `@tauri-apps/plugin-store` (a real JSON file in the OS app-data directory, not `localStorage`). On every cold start, `timerStore.reconcile()` treats the SERVER's `GET /api/time/entries/active` as ground truth and the local marker only as a hint for exactly which local details to preserve (the in-progress segment's start time, the task memo) when the server confirms a session is still running — never the other way around. Concretely: server says running + local marker matches → resume seamlessly, no notice. Server says running + no/mismatched local marker → resume anyway, but tell the VA ("Resumed a timer that was already running on the server"). Server says nothing running + a local marker claimed otherwise → clear it and say so ("...had already ended and wasn't resumed") rather than silently dropping it. A queued op still sitting in local storage for a session the server no longer shows as running (a Stop that hasn't synced yet) is excluded from "sessions to resume" — reconcile() flushes the queue BEFORE deciding what's running, precisely so a not-yet-synced Stop is never mistaken for "still going."

**Four real bugs found building and testing this, each worth its own note:**

1. **The `keyring` crate silently no-ops without an explicit platform feature flag.** `keyring = "3"` (no features) compiles cleanly on macOS and every `save`/`load`/`clear` call returns `Ok` — but nothing actually reaches the Keychain; the crate has no default backend. Confirmed empirically: `security find-generic-password` found nothing after a "successful" save. Fixed with `features = ["apple-native", "windows-native", "sync-secret-service"]` in `Cargo.toml`; each is gated by its own `cfg(target_os = ...)` so enabling all three is portable, not macOS-only. A real, from-scratch Rust `#[test]` (`round_trips_through_the_real_os_keychain`) now exercises the actual OS keychain on every `cargo test` — this is the one thing in this app that would be dishonest to mock.

2. **`offlineQueue.flush()` could silently lose an op enqueued while it was running.** The original implementation took one snapshot of the pending-ops list at the start of a run and wrote that (now-stale) list back when it finished — so a segment enqueued mid-flush (e.g. a rollover tick firing during `stop()`'s own flush) was invisible to the in-flight run's snapshot, and got overwritten out of existence when that run finished and persisted its stale view. Reproduced directly: a resumed session's final segment vanished with no error logged. Fixed by having `flush()` re-read the pending-ops file fresh on every iteration and remove completed ops by id against another fresh read, both under a single write lock shared with `enqueue()`.

3. **A second, related bug in the same area: `flush()`'s reentrancy guard let an explicit `await` return before the real work finished.** The `if (flushing) return` pattern meant that if `enqueue()`'s own fire-and-forget `flush()` call was already running, a caller that explicitly awaited `flush()` (`stop()`, specifically) got back an already-resolved no-op promise — not a promise that actually waited for the real one to finish. Caught directly while testing session resume: `stop()`'s caller (a test standing in for the app calling `logout()` right after) believed the queue had been given its chance and moved on, while the real flush was still using the now-cleared session and failed. Fixed by coalescing concurrent callers onto one shared in-flight promise (a module-level `flushPromise`) instead of the boolean guard — every caller now genuinely awaits the SAME run.

4. **Two format mismatches between what the desktop app sent and what the existing time-tracking API (built and tested in a browser context) expected.** `createSegmentSchema`'s `memo` field is `z.string().optional()` — omittable, but not `.nullable()` — so sending an explicit `memo: null` (this app's natural "no task set" representation) failed validation; fixed in `apiClient.ts` by omitting the key entirely rather than nulling it (`JSON.stringify` already drops `undefined` keys). Separately, `segmentStart`/`segmentEnd` sourced from a server response (`session.startTime`, a Postgres timestamptz serialized as `"...+00:00"` with microsecond precision) don't match the exact form `z.string().datetime()` requires by default (JS's own `toISOString()`, millisecond precision, `"...Z"`) — fixed by re-stamping every server-sourced timestamp through `new Date(x).toISOString()` in `timerStore.ts` before it's ever used as a segment boundary. Both were invisible in the previous phase's own test pass because that phase only ever exercised the API from the browser's cookie-authenticated Server Actions, which never round-trip timestamps through this exact serialize/deserialize path.

**Testing approach — no GUI available in this environment.** This sandbox has no interactive WindowServer session: `tauri dev` compiles and launches the real binary cleanly (confirmed via its build output), but the process exits immediately rather than showing a window, since there's no display to attach to. That's an environment limitation, not evidence about the code, so verification leaned on what's actually checkable here: `cargo test` against the real OS keychain (above), and a Node test harness (`node --import` with `tsx/esm/api` plus a small custom module hook) that imports this app's actual TypeScript modules — `authStore`, `apiClient`, `timerStore`, `offlineQueue`, `placementsStore` — completely unmodified, and drives them against the real local Supabase + Next.js dev server. Only the two Tauri-native bindings (`@tauri-apps/api/core`'s `invoke`, `@tauri-apps/plugin-store`'s `load`) are swapped for file-backed fakes mirroring their real semantics — deliberately file-backed, not in-memory, so that separate `node` process invocations can genuinely simulate "the app was killed and relaunched" the same way the real OS keychain and the real plugin-store file would survive that.

## Screenshot capture in the desktop app

Adds periodic screenshot capture to `apps/desktop`, entirely on top of the existing backend from the time-tracking API phase — `uploadScreenshot()` and its private-bucket/signed-URL/one-per-segment design were already built and tested; this phase only had to call it correctly from a real OS-level capture pipeline. No backend changes were needed.

**Recommendation: primary display only, not all connected monitors — implemented as such.** The deciding factor is that the existing backend enforces exactly one screenshot per segment (`uploadScreenshot()` returns 409 on a second attempt for the same `time_segment_id`, and the storage path is singular: `{time_entry_id}/{segment_id}.{ext}`). Capturing every monitor would mean either compositing them into one image (extra complexity, larger uploads, awkward across mismatched resolutions/orientations) or changing that already-shipped, tested one-screenshot-per-segment contract. Narrower is also the more defensible privacy default for a v1: capture exactly what's needed to verify work happened, not every screen a VA has open, and widen later (e.g. an admin/client-configurable "capture all displays" opt-in) only if an actual need emerges. The OS-designated PRIMARY display is detected properly (`Monitor::is_primary()`, not just "whichever one `Monitor::all()` returns first"), so this behaves correctly on real multi-monitor setups rather than being arbitrary.

**Capture pipeline (`src-tauri/src/screenshot.rs`)**: the `xcap` crate (0.9.8) captures the primary display's raw pixels; `image` (0.25) downscales anything wider or taller than 1920px (Lanczos3) and re-encodes as JPEG at quality 75 — screenshots of desktop/text content stay legible well below native resolution, and this keeps typical uploads in the tens-to-low-hundreds-of-KB range, comfortably under the existing 15MB cap. The result crosses the Tauri IPC boundary as base64 (simplest reliable option for a modest, already-compressed payload; not worth a raw-byte-transfer optimization at this size).

**Randomized per-segment timing, done without a second timing mechanism.** A random offset within `[0, SEGMENT_ROLLOVER_MS)` (9 minutes, matching the existing segment-rollover margin under the true 10-minute limit) is chosen once per segment window and checked on the SAME 1-second tick that already drives elapsed-time display and rollover — no separate scheduler. The check runs BEFORE the rollover check in each tick so a target reached in a window's last instant still fires against that window instead of being silently skipped when it rolls over later in the same tick.

**Correlating a capture with a segment that doesn't exist yet.** A screenshot is captured mid-window, well before that window's segment is created (segments are only created at rollover). The captured bytes are stashed in local storage (`localStore.ts`'s `pendingScreenshot`, a separate store file from the frequently-rewritten session marker/task, so a keystroke's blur doesn't rewrite a few-hundred-KB blob every time) tagged by the window's start time. At rollover, if a stash exists for the window that just ended, both a `segment` op and a `screenshot` op are enqueued back-to-back, sharing a **client-generated** `clientSegmentId` (the real server segment id doesn't exist yet at enqueue time). `offlineQueue.ts` processes ops strictly in FIFO order and never skips ahead past a network failure, so by the time a `screenshot` op's turn comes, its paired `segment` op has unconditionally already been resolved — synced (its real id is now in a small local `clientSegmentId -> realSegmentId` map) or dropped (nothing to attach to; the screenshot op is dropped too, logged, not retried forever).

**A genuine race found and fixed while building this**: capture is deliberately NOT awaited inline in the 1-second tick (blocking the tick would freeze the visible elapsed-time display for the capture's duration), but the rollover logic that decides "is there a screenshot to attach to this window" runs synchronously in that same tick. Without coordination, a capture scheduled in the same tick as that window's rollover (or a Stop landing right after one was triggered) could still be mid-flight when the attach-check ran, find nothing yet stashed, and the screenshot — once it did finish — would already belong to a window that had moved on, with nowhere left to attach to. Fixed with a small in-flight-capture tracker (`inFlightCapture`, a plain module variable, not store state — pure scheduling plumbing) that rollover and `stop()` both await, for that specific window only, before checking for anything to attach. This in turn required loosening `captureForWindow`'s own "is tracking still genuinely active" check to accept `status === "stopping"` as well as `"running"` — a capture legitimately triggered while running that resolves a moment after Stop has already flipped the status is still for a window that was genuinely being tracked, not a stray capture happening after tracking ended; only `"idle"` or a since-changed window means abandon it.

**"Never capture outside active tracking," structurally, not just as a rule that's hopefully followed everywhere:**
- Capture is scheduled only from inside the same tick loop that already requires `status === "running"` to do anything at all — there's no separate always-on capture timer to accidentally leave running.
- Every capture path re-validates immediately before AND after the actual OS call (`captureForWindow`'s `stillActive()`: status is running/stopping, the window is still current, and an access token still exists) — a screenshot whose conditions changed mid-capture is discarded, never stashed or uploaded, regardless of what the pixels contain.
- **A real, pre-existing gap this surfaced**: nothing previously stopped a running timer on sign-out — `logout()` only ever cleared auth state, so a VA signing out mid-session would have left the tick loop (and its capture scheduling) running against a session with no valid user behind it. Fixed at the UI layer (`App.tsx`'s sign-out handler now awaits `timerStore.stop()` first if a timer is running, before calling `logout()` — which also means the session gets a real final segment and a proper `Stop`, instead of being abandoned) AND independently in the store itself (`stillActive()`'s access-token check means even if some future call site forgets that ordering, capture still can't complete without a valid session) — verified directly: clearing auth state out from under a running timer prevents the OS capture call from ever firing at all, not just discards a result afterward.

**Disclosure**: a one-time acknowledgment (stored via `localStore`'s `screenshotDisclosureSeen`, shown before the very first Start in the app's lifetime) explains what's captured, how often, and who can see it, before any tracking begins. Independently, a persistent "Screenshots are being captured periodically while tracking is active" indicator is shown for the entire duration `status === "running"` — its visibility is driven by the same boolean that gates capture itself, so the disclosure can never be stale (showing when it isn't happening, or silent while it is).

**macOS permission handling — tested for real, with a genuinely useful discovery.** `xcap`'s monitor capture on macOS goes through the legacy `CGWindowListCreateImage` API (confirmed by reading its source, not assumed), which has a well-known quirk: unlike most TCC-gated APIs, it does NOT return an error when Screen Recording access hasn't been granted — it silently returns a fully (or near-fully) black image instead. Detected with a cheap heuristic (sampling ~400 pixels spread across the image; all-black across that sample is treated as "probably blocked," never as "the VA's desktop is legitimately black") that turns that silent failure into a specific `PERMISSION_DENIED` result the UI can act on — an actionable banner with a button that tries the OS's own one-time prompt (`CGRequestScreenCaptureAccess`) and falls back to deep-linking straight to the System Settings pane (`CGPreflightScreenCaptureAccess`/`CGRequestScreenCaptureAccess`, both real public Core Graphics APIs, not private ones) if that doesn't resolve it. Run directly against this machine's real display via `cargo test` (not mocked): capture actually succeeded end-to-end (a real 1920×1249 JPEG, ~288KB), while `CGPreflightScreenCaptureAccess()` reported `false` for that same test binary — a real, empirically confirmed discrepancy (likely this environment's permission being tied to a parent process's grant rather than the freshly-built, unsigned test binary's own). This is exactly why the app treats the preflight check as advisory only and never gates on it proactively — only a genuine capture failure (the `PERMISSION_DENIED` result) drives the actionable banner; trusting the preflight check alone would have produced a false "you need permission" warning on this very machine.

**Windows permission handling — implemented and reasoned from `xcap`'s own source, not empirically verified (no Windows machine in this environment).** `xcap` has two Windows capture backends selectable by Cargo feature: GDI (`BitBlt`-based, the classic screenshot approach, no feature flag needed) and WGC (Windows Graphics Capture, gated behind an opt-in `"wgc"` feature this project deliberately does NOT enable). Full-desktop GDI capture has never been gated behind a runtime consent dialog on Windows — this app's dependency choice keeps it that way on purpose, rather than opting into WGC, which — being the newer, more modern capture path — surfaces a system-level "sharing your screen" indicator/border similar to a Zoom/Teams share, which would be a stronger, more visible signal than this feature calls for. ## Activity monitoring in the desktop app

Adds privacy-conscious keyboard/mouse activity counting to `apps/desktop`, feeding the `keyboardActivityCount`/`mouseActivityCount`/`activityPercentage` fields `createSegmentSchema` already accepted (built in the original time-tracking API phase but never populated by any client until now). No backend or schema changes were needed — same story as the screenshot phase.

**What's recorded, and what never is.** Three aggregate counts per segment: a count of keyboard key-down transitions, a count of mouse button-down transitions, and a count of poll ticks with detected mouse movement — never which key, never any typed text, never a password, never clipboard content, never which UI element was clicked, never a mouse coordinate persisted anywhere. The Rust module's own doc comment states this as an invariant, not just a description: the transient key-code/mouse-position values used to compute a tick's counts live in local variables inside the polling loop and are overwritten every ~100ms, never logged, never persisted, never sent across the Tauri IPC boundary — only the resulting counts are.

**Polling, not a global event hook — a deliberate choice specifically for "must completely stop when the timer stops."** The obvious first choice, `rdev` (a global keyboard/mouse event listener), was tried and abandoned: its `listen()` call blocks forever with no cancellation API at all in the installed version — once started, there is no way to make it stop short of killing the whole process. That's fundamentally incompatible with a hard requirement that tracking stop completely and verifiably when the VA stops the timer. `device_query` instead POLLS current keyboard/mouse state (`get_keys()`/`get_mouse()`, point-in-time OS queries, not an installed hook) from this app's own background thread, at 10Hz (every 100ms). Stopping is then just: set an atomic flag, the thread observes it on its next iteration (within 100ms) and exits — no hook or tap is ever left registered with the OS in between, which is what makes "completely stops" a real, verifiable property rather than an event callback that's merely told to go quiet.

**How the activity percentage is calculated — stated precisely, per the requirement to document it exactly:**
1. While the timer runs, the polling thread samples keyboard/mouse state 10 times per second.
2. Any tick where at least one new key was pressed, at least one new mouse button was pressed, or the mouse moved more than a 3-pixel noise threshold, marks that tick's whole wall-clock SECOND (unix-epoch second) as "active" in a set — a second is only ever counted once no matter how much activity happened within it.
3. When a segment ends (rollover or Stop), the Rust side hands back `activeSecondsCount` (the size of that set) for the window, and is reset for the next one.
4. `activityPercentage = round(activeSecondsCount / segmentDurationSeconds × 100)`, clamped to `[0, 100]`. For a full 9-minute rolled-over segment that's `activeSecondsCount / 540 × 100`; for a shorter final partial segment (Stop before a full window), the real elapsed duration is used instead, so the percentage still means the same thing — "what share of this segment's actual duration showed detected input" — regardless of the segment's length.
5. `keyboardActivityCount` is the raw new-key-press tally for the window. `mouseActivityCount` is mouse clicks PLUS movement-ticks combined (see below for why) — the existing schema has exactly one "mouse activity" column, not two, and splitting it would have meant a schema change this phase didn't need.

**Activity percentage is explicitly NOT a productivity measure — stated as such everywhere it's shown, not just in an internal comment.** The one-time desktop disclosure (shown before a VA's first-ever Start, same mechanism as the screenshot disclosure) says so directly. The Work Diary summary (`apps/web/.../diary-summary.tsx`) now carries a standing caption — "reflects... detected keyboard/mouse input... not a measure of productivity, work quality, or effort" — placed once per page rather than repeated on every block card, plus a `title` tooltip on each block's own Activity/Keyboard/Mouse figures for anyone hovering a specific one. This is a real, load-bearing distinction: a VA reading, thinking, or on a legitimate call shows near-zero keyboard/mouse activity while doing genuine, valuable work — the number describes detected input, nothing else.

**`null`, never a misleading `0%`, when monitoring wasn't available for a window.** If Accessibility permission was never granted, or monitoring failed to start for any other reason, the three activity fields are sent as `null` (a value `createSegmentSchema` already explicitly allows — `.nullable().optional()`, unlike `memo`) rather than `0`. Showing "Activity: 0%" for a window that was never actually measured would read as "measured and found completely inactive" — a materially unfair and misleading signal for a VA whose only issue was an unclicked permission dialog. The Work Diary already rendered `—` for `null` activity fields (built in the Work Diary phase, before any client populated them) — this phase's job was only to make the `null`/real-number distinction actually meaningful.

**A second permission, independent of Screen Recording.** `device_query`'s macOS backend requires Accessibility (`AXIsProcessTrusted`/`AXIsProcessTrustedWithOptions` — the same public, standard API pattern as the Screen Recording check from the previous phase, just a different pane in System Settings). Critically, `DeviceState::new()` (the crate's own unchecked constructor) `assert!`s that this permission is granted and PANICS if it isn't — this module exclusively uses `DeviceState::checked_new()` instead, which returns `None` gracefully, converted here into the same matchable-sentinel pattern (`ACCESSIBILITY_PERMISSION_REQUIRED`) the screenshot module established, surfaced as its own sticky, actionable banner (`activityPermissionIssue`) with its own "Fix this" button (request-prompt, falling back to a direct deep link to the Accessibility settings pane) — separate and independent from the equivalent Screen Recording banner, since a VA could plausibly grant one and not the other.

**On Windows, `device_query` reads `GetAsyncKeyState`/`GetCursorPos` — ordinary Win32 APIs, no elevation or runtime consent dialog, gated behind no feature flag.** Reasoned from the crate's own source, not empirically verified (no Windows machine in this environment) — same standing limitation as the screenshot phase's Windows research, and the same category of API family (classic input-state queries, not a modern capture/share API that would surface a system indicator).

**A real, pre-existing bug found and fixed while testing this — not introduced by this phase, but surfaced by it.** `stopTimer()` (built in the original time-tracking API phase) wrote `ended_at: new Date().toISOString()` computed on the Next.js app server, without ever checking it against the row's own `started_at`. The app server and the database run as different processes with independently-drifting clocks (in local dev, literally a different machine: a Docker container vs. the host) — for any realistic session (seconds to hours) that drift is irrelevant, but a session started and stopped within milliseconds of each other (exactly what this phase's own rapid start/stop/start/stop test sequence does, deliberately, to exercise the lifecycle quickly) could have `ended_at` land measurably BEFORE `started_at`, tripping the `time_entries_end_after_start` CHECK constraint. The consequence was serious for something so narrow: the failure surfaced as a generic 403, which the offline queue correctly classifies as "the server permanently rejected this — drop it, don't retry forever" (exactly right for a genuine RLS/business-rule rejection) — but for THIS failure, retrying the identical payload would have failed identically every time, permanently orphaning that time entry as "running" server-side forever with no way for the client to recover it. Fixed by reading `started_at` first and clamping `ended_at` to `max(now, started_at + 1ms)` — the `+1ms`, not `started_at` verbatim, matters: Postgres stores microsecond precision, round-tripping through a JS `Date` truncates to milliseconds, so re-submitting the truncated value verbatim could itself still land a few microseconds short of the real stored value and trip the same constraint. Verified by intentionally reproducing the original failure (consistently, across a full local dev day's clock drift) before the fix and confirming zero recurrences across 12 back-to-back rapid start/stop cycles after it. A secondary, permanent improvement made alongside this: the previously-silent `error` case in `stopTimer()` now logs the actual Postgres error server-side — this specific bug was undiagnosable without that until it was added.

**CPU/memory — measured for real, with one honest caveat.** This sandbox has no interactive way to grant a macOS TCC permission (no GUI to click "Allow," and directly editing `TCC.db` would require disabling System Integrity Protection — a system change well outside what this phase should do unprompted), so the literal `device_query` polling loop couldn't be measured running live here; `start_activity_monitoring()` correctly, verifiably refuses to run without it (see the Rust test `start_stop_lifecycle_is_safe_and_idempotent`, which asserts the specific error rather than skipping silently). Measured instead: a shape-equivalent synthetic loop — same 10Hz cadence, same `HashSet` diff/insert pattern against a same-sized synthetic key set, same mutex lock, same sleep — which is a fair, if not slightly conservative, proxy (hashing/diffing a small `HashSet` is comparable to or pricier than the actual `GetAsyncKeyState`/`CGEventSourceKeyState`-style OS query it stands in for). Result, sustained over 15 real seconds: ~0.10% average CPU, ~9.7–9.95MB RSS, flat (no growth) after the first couple of seconds — see `measure_resource_usage_synthetic_equivalent_loop` in `activity.rs`, runnable directly via `cargo test --release -- --ignored --nocapture`.

## Offline resilience in the desktop app

Makes the desktop timer survive a lost connection and an unclean shutdown without either silently losing tracked work or silently inventing it. The offline queue itself (FIFO, local-first, retry-vs-drop classification) already existed from the original timer phase; this phase closes the two gaps that design alone didn't cover — a *retried* request creating a duplicate, and a *lost* app session leaving no honest record of how much time was actually verified.

**Idempotency keys, not just "queue it and hope."** A queued op can be resent for a reason the client can never fully distinguish: the original request never reached the server, or it reached the server and succeeded but the response never made it back (connection dropped mid-flight, app killed right after). Blind retry-on-failure, which is what the queue already did, is only safe if the server can recognize a resend as *the same* request. `time_segments` gets a client-generated `client_segment_id uuid` column (`segment_idempotency` migration) with a **partial unique index** (`where client_segment_id is not null` — existing/historical rows have none and stay valid; a plain `UNIQUE` would work too since Postgres already treats NULLs as distinct from each other, but the partial index says so explicitly and keeps the index smaller). `createSegment()` checks for an existing row by that id FIRST and returns it as-is if found — a retry becomes a no-op read, not a second row — and if two attempts race past that check simultaneously, the one that loses the unique-constraint race catches Postgres's real `23505` error and fetches/returns what the winner just inserted, rather than surfacing a confusing failure for what is, from the caller's perspective, the exact request they already made. `createSegmentSchema` now requires `clientSegmentId`; the desktop app already generated one per segment for local screenshot-pairing purposes (previous phase) — it's now the SAME id sent to the server, not a second one to keep in sync.

**`uploadScreenshot()` gets the same treatment, but with two failure points instead of one.** An upload is upload-then-insert — a retry can be resuming from either half having partially completed. Three cases, all now idempotent-safe: (1) a screenshot row already exists for the segment → return it directly (this used to `throw 409`; a *retry* reading "already done" as an error was itself a bug this phase fixes, not just an omission — see the updated `apps/desktop`-facing behavior below). (2) The storage object already exists but no DB row does (a prior attempt uploaded the file, then died before the insert) → treated as "the file's already there, proceed to the insert," not a fatal error; detected via Supabase Storage's real conflict shape (`statusCode: "409"` / message containing "already exists" — confirmed empirically against the local Storage API, both raw and through `@supabase/supabase-js`). (3) A genuine insert-time race with a concurrent request → same unique-violation-catch-and-fetch pattern as segments, and — importantly — the file is NOT deleted in this case (only a genuinely orphaned file, with certainly no row pointing at it, is ever cleaned up). The storage path was already fully deterministic (`{time_entry_id}/{segment_id}.{ext}`, not random) from the original phase, which is exactly what makes retrying safely target the same object instead of accumulating orphans.

**A previously-thrown 409 becoming a returned success is a real behavior change, checked against what actually depends on it.** The offline queue already classified a non-network 4xx as `"dropped"` (permanently given up, logged) — so a retried screenshot op that used to hit the 409 was already being removed from the queue either way; the change is that it's now removed as a correctly-recognized success instead of a misleadingly-logged rejection. Nothing downstream distinguishes those two queue outcomes today, so this is a pure improvement, not a compatibility risk — verified directly (see Verification below).

**`lastSeenAt`: the one fact stale-session recovery is built on.** `ActiveSessionMarker` (the local crash-recovery breadcrumb, previous phase) gains a `lastSeenAt` ISO timestamp, stamped fresh on every write — every rollover, every `setTask()`, every `start()`/resume, and now also a dedicated 30-second heartbeat in the tick loop so it never goes stale for the full length of a long, event-free segment (up to 9 minutes between rollovers otherwise). On relaunch, this is the one thing the app trusts about its own past: not what the marker *assumed* was still happening, but the last instant this process can actually prove it was alive and tracking.

**Stale-session reconciliation: resume vs. close, decided by how large the gap is.** `reconcile()` already resumed a session whose local marker matched a still-running server entry (previous phase); this phase adds a check before doing that unconditionally. If `now - lastSeenAt` is under a threshold (90 seconds — comfortably more than one heartbeat interval plus normal network/IPC jitter), the gap is treated as an ordinary brief interruption and resumed exactly as before. Past that threshold, resuming as-is would be actively wrong: `onTick()`'s rollover loop measures elapsed time purely against wall-clock `now`, so replaying it against a `currentSegmentStart` left stale by a real crash would fabricate however many complete 9-minute segments the gap spans — segments with no observation behind them at all, the literal definition of invented time. Instead, `closeStaleSession()` closes the entry at the last VERIFIED checkpoint: if any real time elapsed between the open window's start and `lastSeenAt`, that stretch becomes one genuine final segment (with `null` activity — the Rust-side counters are in-memory only and don't survive a crash, so "not measured" rather than a fabricated number); nothing after `lastSeenAt` is ever turned into a segment at all, not created-then-discarded, simply never created. `stopTimer()` gains an optional `endedAt` (validated by a new `stopTimerSchema`, sent only by this path — a normal Stop-button click still omits it and gets the server's own clock, unchanged) clamped server-side to `[startedAt, now]` so a client can never claim a future-dated end. The VA is always told what happened — a short gap resumes with "recovered with no tracked time lost," a long gap closes with a message naming the actual checkpoint time and stating plainly that time after it wasn't counted — never a silent resume, since reaching this code path at all means the app went away without a clean Stop.

**Corruption resilience: every local read degrades to a safe default, never a crash.** `localStore.ts`'s getters (`getActiveSessionMarker`, `getPendingOps`, etc.) now validate shape, not just presence, before trusting what comes back — realistically triggered not by adversarial tampering but by an app upgrade meeting data an older version wrote (this phase's own `lastSeenAt` field is a live example: a marker written by the previous phase's build, read by this one, is now missing a required field and gets correctly rejected rather than fed as `NaN` into the stale-gap math). `getPendingOps()` validates each queued op individually and drops only the malformed ones — a partial-write crash much more plausibly corrupts one record than invalidates a whole queue of real, unsynced work. Read failures (a store that fails to load at all) no longer poison the module forever either: the load promise is only cached on success, so a failed attempt lets the next call retry rather than every future read failing identically for the rest of the process's life. (The production Tauri store plugin, it turns out, already discards unparseable on-disk JSON and starts empty rather than erroring — confirmed by reading `tauri-plugin-store`'s own Rust source — so this mostly guards shape-drift across app versions and defends against a dependency's behavior changing, rather than a gap the plugin currently has.)

## Weekly timesheets (`weekly_timesheets` migration)

Adds a `timesheets` table — one row per (placement, ISO week) — carrying a review status (`OPEN → SUBMITTED → APPROVED → LOCKED`) and, once locked, a frozen snapshot of that week's Tracked/Approved/Rejected/Pending hours. This is new state layered on top of the existing time-tracking backend (`time_entries`/`time_segments`) and the Work Diary's own hour-bucketing logic — no changes to either.

**Hours are computed live, not stored, until the moment a week is locked — the single most consequential design decision in this feature.** An OPEN/SUBMITTED/APPROVED timesheet's four hour columns stay `NULL`; the admin and client pages both compute Tracked/Approved/Rejected/Pending fresh from `time_segments`/`time_entries` on every read (`computeTimesheetHours()` in `server/queries/shared/timesheet-hours.ts`), the same "derived, not stored" convention the Work Diary interface already established. Storing a running total from the start would mean keeping it in sync with every new segment, every re-approval, every offline-queued segment that syncs late from the desktop app — a staleness bug waiting to happen, for numbers that are explicitly *allowed* to keep changing right up until lock. `timesheets_locked_has_snapshot` (a table CHECK constraint) makes the other half of this structural: a row cannot BE `LOCKED` without all four hour columns already populated — there is no code path that reaches `LOCKED` with stale or missing numbers.

**"Historical tracked time should not silently change" is enforced by removing the ability to change it silently, not by a rule asking nobody to.** `timesheets` has no `UPDATE` policy at all — for any role, admin included — and, independently, no `UPDATE` grant either (Postgres checks table-level grants before RLS ever runs; see the `fix_baseline_grants` precedent this deliberately does NOT repeat here). The only two ways a timesheet's status or hour columns can ever change are `admin_set_timesheet_status()` and `admin_correct_locked_timesheet()`, both `SECURITY DEFINER` (so they bypass the missing grant/policy the same way `admin_update_placement_rates()` bypasses the missing `agency_margin` column grant), and both write an `audit_logs` row in the *same transaction* as the change they make. This is stricter than the column-`GRANT` pattern used for `jobs.agency_margin`/`time_segments`' boundary columns elsewhere in this schema, specifically because "any administrative correction after locking must create an audit record" is a hard requirement here, not a convention worth trusting a caller to remember — there is no plain-`UPDATE` code path that could be added later and quietly skip the audit row, because there is no plain-`UPDATE` code path at all.

**Status transitions are forward-only, one step at a time, computed and enforced entirely inside `admin_set_timesheet_status()`.** `OPEN → SUBMITTED → APPROVED → LOCKED`, never backward, never skipped — the function reads the current status, looks up the single allowed next value, and raises a specific error naming both the current status and the only valid next one if the caller asks for anything else. Locking is the one transition that also computes the hour snapshot, in the same statement/transaction as the status flip — not as a separate step — so there is no window between "compute the totals" and "persist them" where a concurrently-syncing segment (the desktop app's offline queue, resolving something backlogged) could land and produce a snapshot that never actually matched what was live at the instant of locking. Segment boundaries are compared against explicit UTC instants (`week_start::timestamp at time zone 'UTC'`, not a bare `date::timestamptz` cast) — the latter depends on the database session's timezone setting; the former doesn't, matching how every other week boundary in this app is computed.

**A week is not "for each active placement" in the narrow, literal sense once you consider history.** Generating timesheets for a week (`ensureTimesheetsForWeek()` in `server/queries/admin/timesheets.ts`, an idempotent upsert with `ignoreDuplicates: true` run automatically at the top of every admin timesheets-list read — this app has no cron/job-runner infrastructure, so there is no separate scheduled generation step or manual "Generate" button) creates a row for a placement if EITHER it's currently `ACTIVE` (so a VA with zero tracked hours yet this week still gets a visible `OPEN` row) OR it has at least one real `time_segment` landing in that week regardless of the placement's *current* status (so navigating to a past week still shows timesheets for a placement that has since ended — the ordinary case of reviewing history after an assignment wraps up). The client-facing read path (`getClientTimesheetsForWeek()`) deliberately does NOT generate anything — `timesheets` has no `INSERT` policy for `CLIENT` at all — so a week an admin hasn't reviewed yet simply shows nothing to a client, never silently materializes on their behalf.

**"Allow admin to approve/reject questionable time"** reuses columns that have existed since the very first time-tracking migration and were never once written: `time_entries.status`/`approved_by`/`approved_at`. Grepped exhaustively before writing this migration — genuinely write-once-at-`'pending'` until now. `admin_set_time_entry_status()` sets all three together (clearing `approved_by`/`approved_at` back to `NULL` on a reset to `'pending'`) and audit-logs itself, same `SECURITY DEFINER` self-contained pattern as the timesheet RPCs — even though admin's existing blanket `time_entries_admin_all` policy would technically already allow a plain `UPDATE` here, routing it through one function means there is no plain-`UPDATE` path this action could ever be reached through that skips the audit row. This is deliberately allowed regardless of the entry's week's timesheet status: approving/rejecting an entry after its week is `LOCKED` has *no effect* on the frozen snapshot unless an admin also explicitly runs `admin_correct_locked_timesheet()` — the one, narrow, always-audited path — which keeps the "don't silently change locked history" guarantee intact without needing a special-case guard on the entry-status RPC itself. Verified directly: approving an entry after its timesheet was locked left the stored snapshot completely unchanged; only the explicit correction call changed it, and only with a reason.

**Clients can view tracked work but structurally cannot touch a rate — there is nothing rate-related on this table for them to reach.** `timesheets` has no dollar-amount or rate column at all, in any state; the client read path (`getClientTimesheetsForWeek`) queries placements through `client_placements_view` (no `client_hourly_rate` column, per the rate-privacy mechanism documented earlier in this file), never the base `placements` table or `admin_placements_view`. "Clients can't manipulate financial rate calculations" is satisfied the same way `va_hourly_rate` being a generated column makes it impossible to write directly — not a permission a client happens not to have, a value that was never in reach to begin with.

## The weekly invoice engine (`weekly_invoices` migration)

Turns a client's `LOCKED` weekly timesheets into a real invoice: `Approved Billable Hours × Placement Client Hourly Rate`, one line item per placement, one invoice per (client, week). Sits directly on top of the previous phase — locking a timesheet was always "locked *for invoicing*"; this is that causal link made real.

**The precision bug this phase found in its own, just-shipped predecessor.** "38 hours 20 minutes" is 38.3333... hours (repeating) — `timesheets.approved_hours` (`numeric(8,2)` at the time) rounds that to 38.33, which at $6.00/hr gives $229.98, not the correct $230.00. Two decimal places is fine for a human-readable weekly summary; it is measurably too lossy to bill from. Fixed by widening every hours column that feeds a dollar calculation to `numeric(10,4)` (`timesheets`' four hour columns, `invoice_items.hours`) and re-deriving `admin_set_timesheet_status()`'s lock snapshot at that precision — rounded once, at the moment of freezing, never re-rounded downstream. `invoice_items.amount` stays `numeric(12,2)` and un-wrapped (`hours * rate_hour`, no explicit `round()`, matching the original invoicing migration's own style) — Postgres rounds to the column's declared scale on store, which is the ONLY rounding step in the whole pipeline from tracked segment to billed cent. Verified against the exact worked example: 230 real ten-minute segments (38h20m), locked, invoiced at $6.00/hr → `hours=38.3333, amount=$230.00` — exactly, not approximately. All of this is Postgres `numeric` (exact decimal) end to end; the application layer never performs the multiplication itself, in JS `number` or otherwise — it only ever displays a dollar amount Postgres already computed.

**Immutability, same shape as timesheets, extended one level further.** `invoices`/`invoice_items` have no `UPDATE` grant and no `UPDATE` policy at all — the only ways either table changes are `admin_generate_weekly_invoice()` (creates a new invoice + its line items, atomically) and `admin_set_invoice_status()` (the status lifecycle only), both `SECURITY DEFINER`, both self-audit in the same transaction as the change. `invoice_items` has no `UPDATE` path *of any kind*, not even an RPC — unlike a timesheet, which has one narrow, audited correction escape hatch, an invoice's line items are immutable from the moment they're generated. The intended correction path is `VOID` the invoice and generate a new one, not edit a historical financial document in place — noted below as the deliberate absence it is, not an oversight.

**Rate snapshots, same reasoning applied one column further than the original invoicing migration went.** `invoice_items.rate_hour` (the client rate) was already a snapshot, not a live join to `placements` — the original migration's own comment says so. This phase adds `va_hourly_rate` as a second snapshot, plus two columns generated from it: `va_payout_amount` (`hours × va_hourly_rate`) and `margin_amount` (`hours × (rate_hour − va_hourly_rate)`) — by construction, `amount = va_payout_amount + margin_amount` always (verified: `$153.33 + $76.67 = $230.00` on the worked example). Snapshotting rather than joining live to `placements` matters here for the exact reason it already mattered for `rate_hour`: a later admin rate override on the placement must never retroactively change either what the client was already billed or what an admin sees as historical profitability.

**"Client must not see VA payout or agency margin" is a column-GRANT boundary, the same recipe as `jobs.agency_margin`, applied to a table that used to be broadly grantable.** The original invoicing migration's `invoice_items` was part of `fix_baseline_grants.sql`'s broad `select` grant (reasonable at the time — every column on that table was client-safe). Adding `va_hourly_rate`/`va_payout_amount`/`margin_amount` breaks that assumption, so this migration narrows it: `revoke select on invoice_items from authenticated`, then `grant select (the eight client-safe columns)`. A client session querying `va_hourly_rate` directly against the base table gets `permission denied for table invoice_items` — confirmed empirically — not a value a view happened to omit. Admin reads the excluded columns through `admin_invoice_items_view` (`where is_admin()`, view-owner-bypasses-both-RLS-and-grant, identical mechanism to `admin_placements_view`); the client-facing read path needs no equivalent view of its own, since the grant already makes the base table itself client-safe.

**Status is a branching graph, not the single-successor chain timesheets use — `DRAFT → ISSUED → {PAID, OVERDUE} → ...`, with `VOID` reachable from every non-terminal state.** `admin_set_invoice_status()` checks the submitted `(from, to)` pair against an explicit allow-list (`DRAFT→ISSUED`, `DRAFT→VOID`, `ISSUED→PAID`, `ISSUED→OVERDUE`, `ISSUED→VOID`, `OVERDUE→PAID`, `OVERDUE→VOID`) rather than a single "next" mapping. `PAID` and `VOID` are both terminal — no transition out of either, confirmed empirically (`PAID → VOID` rejected). `issued_at`/`paid_at` are stamped exactly once, on the transition that makes them true. There is no scheduled job anywhere in this app (still true this phase) to automatically flip `ISSUED → OVERDUE` once `due_date` passes — that stays a real, explicit admin action; the UI could show a live "past due" indicator without changing the stored status, but that display-only affordance wasn't built this phase (see below).

**One invoice per (client, week), enforced by a real unique constraint, not just an RPC-side check** (`invoices_client_period_unique unique (client_id, period_start)`) — a race between two concurrent generation attempts can't produce two invoices for the same period; confirmed empirically that a second `admin_generate_weekly_invoice` call for an already-invoiced client+week is rejected with a clear message, not a duplicate row. A generation attempt with zero `LOCKED` timesheets (or all locked timesheets showing zero approved hours) is also rejected, and rejected as a full rollback — confirmed no orphaned `invoices` row is left behind when the line-item loop finds nothing to bill, even though the row is inserted before the loop runs.

**Invoice numbering** uses a real Postgres `SEQUENCE` (`invoice_number_seq`), not a `max(...)+1` query or a client-side counter — collision-proof under concurrent generation. Formatted as `INV-{year}-{5-digit sequence}` (e.g. `INV-2026-00001`). Only ever touched from inside the `SECURITY DEFINER` generation function, so it needs no grant of its own to `authenticated`.

**Client portal**: Current Amount Due (`sum(total)` over the client's own `ISSUED`/`OVERDUE` invoices — `PAID` is settled, `VOID` never counted, `DRAFT` is structurally invisible), Invoice History (every non-`DRAFT` invoice, most recent period first), and a per-invoice detail drill-down — all through the same rate-privacy boundary described above, so there is nothing profitability-related on any client-facing page to accidentally leak. `invoices_select_member`'s RLS was updated to add `and status <> 'DRAFT'` — a `DRAFT` invoice is still an admin work-in-progress, and was never excluded from client visibility before this phase because the status lifecycle didn't really have a meaningful "not yet sent" first step until now.

## Internal VA compensation calculation (`va_compensation` migration)

Approved Hours × Placement VA Hourly Rate, alongside the matching Client Revenue and Gross Agency Margin, for admin — and Hours / Their Rate / Expected Compensation, and *nothing else*, for the VA themselves. Explicitly **not** payroll or payment — nothing here transfers money, marks anything paid, or writes to the pre-existing `payments` table. It's a calculation-and-visibility layer, full stop.

**Computed from `timesheets` directly, not from `invoice_items` — a deliberate, load-bearing choice.** The invoice engine (previous phase) already computes and stores this exact shape of number, but only for placements whose client has actually been invoiced for that week. A VA's own compensation for their own approved work shouldn't be gated behind admin's client-billing cadence — invoicing runs on the client's schedule, compensation is about the VA's own locked hours. Both figures agree whenever an invoice IS generated, because both ultimately read the exact same two frozen inputs: `timesheets.approved_hours` (frozen at lock, 4-decimal precision, exact — see the previous two phases) and `placements.client_hourly_rate`/`va_hourly_rate` (an immutable per-placement rate snapshot). Two independent code paths computing from the same frozen source, not one path re-deriving from the other — no risk of the two ever silently disagreeing since neither reads the other.

**Two views, no new table, no new state.** Nothing is stored — `admin_compensation_view` and `va_compensation_view` are plain `SELECT`s joining `timesheets` (`WHERE status = 'LOCKED'`) to `placements`, computing all dollar figures as `numeric` expressions in the view definition itself (`round(approved_hours * rate, 2)`), so the exact-decimal guarantee from the invoicing phase carries over structurally — there is no application code path that performs this multiplication.

**The privacy boundary is column-existence, not column-filtering — the strongest form this schema uses anywhere.** `va_compensation_view` doesn't merely omit `client_hourly_rate`/margin from its `WHERE`-filtered results; the column is never in the view's `SELECT` list at all. Confirmed empirically: a VA session querying `client_hourly_rate` from `va_compensation_view` gets `column "client_hourly_rate" does not exist` — not a permission error, not an empty result, an error stating the column has literally no existence in that relation. This is one step beyond the column-`GRANT` pattern used for `jobs.agency_margin`/`invoice_items.va_hourly_rate` (where the column exists on the relation but a grant blocks reading it) — here there is nothing to grant or revoke, because the view itself was never given that column to begin with. `admin_compensation_view` is the mirror image: all three figures together, gated by `is_admin()` with no membership OR-clause, same shape as `admin_placements_view`/`admin_invoice_items_view`.

**Neither view is reachable by a CLIENT session at all.** No client-facing view exists for this data, and neither view's row-scoping clause (`is_admin()`, `va_id = auth.uid()`) has a client-membership branch — a client session gets zero rows from both, confirmed empirically. "Client must never see VA compensation" holds by the same absence-based reasoning as the VA/client-rate boundary: there is no code path that hands a client session this data, not a filter trusted to catch it.

## Security review (`security_review_fixes` migration)

A full application security review (methodology, every finding, evidence, and fixes) is documented separately in [`docs/security-review.md`](./security-review.md) — start there for the complete writeup. The one piece worth knowing about from this file specifically, because it changes how RLS works schema-wide: **`active_uid()`** is now the standard replacement for `auth.uid()` everywhere a policy or helper function establishes "this is the caller's own row." It returns `auth.uid()` unmodified unless that profile is `suspended`, in which case it returns `NULL` — making suspension a real, database-level access revocation (previously it was enforced only by the Next.js application layer; a suspended user's still-valid JWT could reach the database directly and bypass it entirely). **Use `active_uid()`, not `auth.uid()`, in any new RLS policy or `SECURITY DEFINER` helper function that checks row ownership** — the one exception is the privilege-escalation-prevention triggers (`prevent_self_privilege_escalation`, `prevent_self_approval`, `prevent_client_self_status_change`), which use `auth.uid() is not null` to distinguish a real end-user session from a trusted system context (migrations, the service-role client) and don't need the suspension check for that specific purpose.
